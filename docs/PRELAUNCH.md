# Four-addon prelaunch checks

Protocol **1**, 2026-11-01. This is a first-session procedure and versioned evidence ledger, not a live pass certificate. The client was unavailable during preparation. Offline fixtures cannot certify native secret/taint enforcement, rendering, real event cadence, frame time or predictive usefulness.

2. Test the existing-settings path first. Install the candidate with the client closed, enable the four addons and log in. Keep other addons and UI scale documented. Record any compatibility/migration notice before proceeding.
3. Test fresh settings separately, using a clean test account/profile or a backed-up test installation. If reusing a test installation, move the four addons' applicable SavedVariables files **and `.bak` companions** aside only while the client is closed. Do not delete the originals or alter native layout files. A new character alone does not clear account-wide addon settings.
4. For Learn, an older `0.1.6`-or-earlier corpus being rejected with a notice is expected; the enabled setting carries over. A compatible `0.1.7` corpus should rebuild after reload outside combat. Fresh/old corpus rejection is not a prediction-quality result.

## First live session

Run diagnostics before manually refreshing a failed display. `PASS` means the stated observation was reproduced on this exact candidate and client. `FAIL` means captured behavior contradicts an expectation with adequate readable evidence. Use `UNKNOWN` for unavailable/restricted evidence, unsupported formatter/API, absent opportunity, ambiguous timing or insufficient samples. An empty observation is not proof of absence. Preserve an unknown result rather than changing defaults to force a pass.

For the last step, the public read-only status supplies fields not printed by the short slash summary:

```lua
/run local c=BjarkiLearn:Status().core; print(c.modelVersion,c.training,c.modelCorpusRevision,c.corpusRevision,c.modelExamples,c.modelRefreshPending)
```

Read the values in that order. `training=false` with a completed model establishes completion of a serving snapshot, not necessarily a fully current corpus. `modelRefreshPending=true` means another refresh is needed; a bounded rebuild can finish an older snapshot while history keeps changing. There is no promised completion time. Reload saves compatible examples and their stored paired forecasts, not trained weights, optimizer progress or model-version/revision counters. New player scores can therefore be withheld until rebuilding completes and can change afterward as the retained corpus replaces an older serving snapshot; do not require model counters or current scores to stay equal across reload. Stored past forecasts remain the basis for retained paired evaluation. If profiling is unavailable, record performance as unmeasured; the update peak is scoped addon instrumentation, not total frame time or proof of the 1.5 ms soft training budget.

`/bcc test` and `/bp test` are toggleable presentation previews, not live evidence; turn them off before observations. `/bcc used` creates a manual claim and must not be used to manufacture automatic-coverage evidence. Avoid `/blearn reset`, `/bp reset`, `/bcc reset` and `/bcc clear` during evidence collection: they clear learning, settings/positions or tracking needed for interpretation.

## Learn evaluation declared before collecting sessions

The current question is whether **local-player registered readable cast-family deliveries in the next two seconds** are predicted better by the neural model than both the regularized linear/logistic model and smoothed frequency comparator. Families are fear, stun, root, silence, interrupt and defensive. These labels do not mean landed CC, interrupted casts or actual cooldown availability. Enemy positives are separate observations; enemy absence is unknown and enemy examples do not train this model.

- Compare **matched paired forecasts**: all three predictions saved before the same window's outcome, on the same eligible player family/window. Use per-family Brier loss (lower is better), paired count and positive/negative/unknown coverage. Do not compare a model's broad sample with another model's smaller sample. Labels printed as positive/negative are retained coverage totals; they do not themselves give the positive/negative split of the scored subset.
- A score requires at least two player positives and eight negatives in the completed serving model snapshot. This support floor only permits a diagnostic score; it is not enough to establish calibration or practical value. Sparse positives, easy negatives or a low pooled loss do not establish success for a rare family.
- Before each collection block record the class/activity, candidate, settings, serving model/corpus revisions, planned session count and observation duration. Collect multiple sessions with varied encounters. Report each family's counts and each session separately, including withheld/unknown families. A provisional improvement requires lower paired neural loss than **both** comparators repeatedly for adequately represented families, without added runtime errors/cost or changed native behavior. Otherwise record no demonstrated advantage. This first-session procedure does not authorize a forecast-driven consumer or a claim of calibrated probabilities.
- `/blearn status` recomputes losses from the bounded **currently retained** examples (maximum 256). Corrections can revise labels/evaluation, pruning can remove contributions, compatible reload can restore retained forecasts, and serving-model support can differ from current coverage. Snapshots overlap and are **not independent cumulative batches**: never sum their counts, average their losses as independent sessions, or infer new-sample loss from their differences. There is no built-in immutable per-session evaluation export here. Preserve chronological snapshots as diagnostics; a stronger disjoint-session/held-out analysis needs an explicitly defined data-collection method before any acceptance claim.

## Recovery

If a failure blocks play, save the available status/error and candidate identifier first. Fully exit **all affected clients** before disk changes; a running client can overwrite an on-disk restore at logout. Preserve the failed candidate and settings as a separate evidence copy.

Restore the complete original addon folders **and their compatible saved settings together**, including `.bak`, from the same backup checkpoint. Restore the corresponding native layout/CVar files only if they were changed, using the complete WTF backup; do not erase or replace native layouts as an addon workaround. Restore only while closed, then log in and confirm versions, settings and the specific affected behavior. A files-only rollback can retain newer settings and fail to reproduce the older configuration. Do not paste the historical 0.4.17 recovery `/run` settings into this candidate as current defaults; [that recovery record](https://github.com/bjoern-janson/bjarkiCC/blob/55b800b66b70b6ffb00f79fedfb34da9ba2bdc12/RECOVERY.md) applies to its named older runtime.

If isolating the cause, disable one addon through the addon list and reload outside combat; record the exact combination. Retain the evidence, restore the intended configuration afterward and repeat the triggering action. A quiet session after disabling an addon narrows the comparison; it does not diagnose a code path.
